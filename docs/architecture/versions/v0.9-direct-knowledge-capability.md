## 变更摘要

v0.9 是一次破坏性内部协议升级。Agent 的能力意图从旧工具请求改为 `CapabilityCall`，
阶段服务补齐运行身份后构造 `CapabilityRequest`，`DefaultCapabilityGateway` 直接执行显式注册
的 `knowledge.search` 和 `payment.calculate`。政策检索不再经过旧工具名、同步 payload 适配或
旧结果投影；政策证据只从 `CapabilityResult.output["evidences"]` 进入工作流状态和最终答案。

## 完整架构

系统仍是 CLI Agent Harness。`ask`、`eval`、`chat` 和 `version` 通过项目协议工作；默认
`LangGraphWorkflowRuntime` 与显式 `NativeWorkflowRuntime` 共享阶段服务、reducer、
`CapabilityGateway`、`KnowledgeGateway`、`TraceEvent`、Usage 和 Eval 协议。

```text
NativeWorkflowRuntime -----|
                           +-> shared stages
LangGraphWorkflowRuntime --|       |
                                   +-> CapabilityCall
                                       -> CapabilityRequest
                                       -> DefaultCapabilityGateway
                                           +-> knowledge.search -> KnowledgeGateway
                                           +-> payment.calculate -> calculate_payment
                                   +-> TraceRecorder / RunProgressEvent
                                   +-> WorkflowState / EvidenceItem
```

LangGraph 只调度项目阶段。LangGraph 专有 StateGraph、message、Command、channel、checkpoint
类型不得进入领域、应用、Agent、能力、Prompt、Trace 或 Eval 公共协议。

## 能力协议和调用链路

### Agent 意图

Agent 无状态，只返回 `AgentMessage`。需要能力时填充 `capability_calls`：

```text
CapabilityCall
  call_id
  capability_name
  called_by
  input
```

当前能力名称只有：

| 能力名 | caller | 风险 | handler |
|---|---|---|---|
| `knowledge.search` | `PolicyRAGAgent` | `read_only` | 注入的 `KnowledgeGateway.search()` |
| `payment.calculate` | `PaymentCalculationAgent` | `calculation` | 确定性待遇测算函数 |

Agent 不直接调用 KnowledgeGateway、测算函数或第三方 SDK。`NativeStageServices` 将
`CapabilityCall` 转换为 `CapabilityRequest`，加入 `run_id`、`request_id`、`session_id`、
`node_id`、`logical_call_id`、`attempt`、runtime 名称和版本。

### CapabilityGateway

`DefaultCapabilityGateway` 是 Runtime/阶段服务依赖的唯一能力执行端口。执行顺序为：

```text
显式注册查找
  -> caller 权限
  -> 必填输入
  -> logical_call_id 幂等缓存
  -> timeout
  -> handler
  -> 输出字段和能力专属输出校验器
  -> capability started/finished/failed trace
```

`CapabilityRegistry` 是显式白名单，不支持任意运行时发现。未知能力返回
`capability_not_registered`；非法 caller 返回 `caller_not_allowed`；输入或输出结构错误、
同一逻辑调用改变能力/调用方/输入返回 `logical_call_conflict`；超时和 handler 异常均返回稳定的
`CapabilityResult.error.code`。未注册能力在幂等缓存之前拒绝，不读取既有逻辑调用缓存。

`CapabilityResult` 的公共字段为：

```text
schema_version
request_id
session_id
capability_name
caller
node_id
logical_call_id
attempt
status
policy
output
error
reused
```

不存在旧工具结果嵌套字段。`output` 是唯一能力业务结果来源；失败原因只写入 `error`。
同一 run 的同一 `logical_call_id` 重试复用历史结果，第二次结果标记 `reused=true`，
`attempt` 仅表示物理尝试次数；每个物理 attempt 都发布自己的 started/finished/failed 生命周期事件，
但 handler 只执行一次。

## KnowledgeGateway 与政策语料

`KnowledgeGateway` 是框架中立 async 端口，输入为显式构造的 `KnowledgeQuery`，输出为
`KnowledgeSearchResult`。`LexicalKnowledgeGateway` 读取 `policy-corpus.v1` JSONL，在可信元数据
过滤后执行可解释 lexical 召回。

`knowledge.search` handler 只读取 `trusted_jurisdiction` 构造查询：

```text
tenant
+ jurisdiction
+ effective_at
+ review_status=approved
+ audience_role
+ source_type=official
+ document_version
```

模型从用户文本抽取的省、市只能作为候选事实，不能覆盖请求中的 trusted jurisdiction。
没有可信地区时，KnowledgeGateway 返回 `no_trusted_jurisdiction_match`，不扩大到全国政策。

检索顺序固定为：

```text
trusted metadata filter
  -> lexical baseline
  -> EvidenceItem
  -> citation validator
```

`KnowledgeSearchResult` 只保留 `evidences`、`corpus_version`、`applied_filters` 和
`no_result_reason`。每个 `EvidenceItem` 必须保留 evidence ID、文档 ID、标题、条款、原文、
地区、有效期、审核状态、版本、来源 URL、语料版本、证据 hash、召回方式、lexical score
和 citation。无结果不得伪造 Evidence。

## WorkflowState 和答案链路

`WorkflowState.capability_results` 保存 `CapabilityResult.model_dump(mode="json")`；
reducer 按 `logical_call_id` 合并能力结果，按 `evidence_id` 合并证据。
`WorkflowState.evidence` 直接保存 EvidenceItem 投影，不再保存旧工具或旧结果包装。

答案聚合规则：

1. 从 `knowledge.search` 的 `output["evidences"]` 收集引用。
2. 从 `payment.calculate` 的 `output` 收集确定性测算项目。
3. 没有政策 evidence 时走保守答案，即使存在测算结果也不得给出待遇承诺。
4. 引用校验失败、地区不一致、安全守卫失败或能力失败时使用项目定义的 StopReason。

## 双运行时边界

Native 与 LangGraph 复用同一个 `NativeStageServices`、同一个能力协议和同一组合根注册
能力；每个 runtime 保持独立的 `DefaultCapabilityGateway` 实例与幂等缓存，避免差分运行互相污染。
LangGraph 只把每个阶段调用映射为图节点，再调用项目 reducer；不实现第二套能力路由、第二套状态
合并或第二套 trace。

允许差异仅包括 runtime 名称/版本、TraceEvent ID、时间、毫秒延迟和框架内部事件顺序。
能力名称、能力输入、logical call ID、Evidence ID/内容、StopReason、最终业务状态和安全结果
必须一致。

## Trace、Usage、Badcase 和 Eval

能力执行通过 `RunEventSink` 发布：

```text
capability_started
capability_finished
capability_failed
```

事件携带 run、request、session、runtime、node、logical call 和 attempt 身份。默认 CLI 路径
由能力网关将 capability 事件投影到项目 trace；Textual TUI 通过组合 sink 统一写 trace 和队列，
不产生第二份能力 trace。

RAG eval 继续独立报告 Recall@K、MRR、引用支持率、可信过滤率和无结果安全率。
Runtime differential eval 使用同一 `eval_cases.jsonl`，当前验收结果为 30/30 equivalent、0 different。

Badcase 按 `knowledge.search` 无结果、能力失败、缺引用、安全拦截和空答案分类。TaskState、
RunReport、SessionState、TraceEvent 和 Eval artifact 继续职责分离，不互相替代事实来源。

## 相对 v0.8 的差异

1. 删除旧工具请求和结果协议，Agent 使用 `CapabilityCall`。
2. 能力名统一为 `knowledge.search` 和 `payment.calculate`。
3. 删除旧工具注册表、旧执行器、旧政策同步 handler 和旧结果投影。
4. `DefaultCapabilityGateway` 直接执行显式注册能力，保留权限、超时、输出校验、幂等和 trace 治理。
5. `CapabilityResult.output["evidences"]` 成为唯一政策证据入口。
6. WorkflowState、答案聚合、badcase、CLI/TUI 和 Eval 全部消费 capability 语义。
7. Native/LangGraph differential eval 继续作为发布门禁。

## 兼容性与迁移策略

这是内部破坏性升级，不提供旧符号兼容：

- 旧工具名、旧函数、旧输入转换方法和旧输出投影被删除。
- 旧测试和旧 fixture 回放入口被删除；RAG eval 使用 `policy-corpus.v1` 和结构化 Evidence。
- v0.8 版本正文作为只读历史保留，不作为 v0.9 运行时输入协议。
- 不对旧运行状态做静默转换；需要恢复旧状态时必须先建立显式版本化迁移协议。

## 已知限制

当前语料仍是小规模、人工审核的离线政策基线，不是持续更新的生产知识库；当前只启用 lexical
baseline，不支持 embedding、vector store、fusion、reranker、自动审核和在线抓取。真实模型
Smoke Eval 与离线能力协议验收分开执行，离线结果不代表生产法规覆盖率。
