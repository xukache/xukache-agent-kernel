| 字段 | 内容 |
|---|---|
| 架构版本 | v0.1 |
| 主题 | Memory scope、会话隔离与跨会话共享 |
| 日期 | 2026-07-15 |

## 2. 变更原因

当前 Kernel 已确认六个核心原语和单向依赖，但 Memory 的 scope、数据可见性和跨会话
共享仍停留在描述性边界。该缺口会直接影响 AgentDefinition、AgentInput、Memory
Protocol、Adapter 分区、权限检查和 RD-004 验收，因此需要发布完整架构基线。

## 3. 架构目标与约束

- 使用六个核心原语表达通用 Agent Kernel。
- Kernel 不依赖 Application、Interface、Provider SDK 或具体存储。
- Application 负责装配 Definition、Adapter、Policy 和主体身份。
- Runtime 负责一次 Run 的生命周期和唯一终态。
- Agent 负责 Model、Tool 和 Memory 的推理闭环。
- Workflow 负责步骤拓扑、流程位置和 WorkflowState。
- Memory 按明确 scope 分区，默认最小可见，不隐式跨会话、用户或项目共享。
- 第一阶段保持单进程、In-memory Memory 和一个真实 Model Provider。

## 4. 完整逻辑架构

```text
External Callers
  -> Interface
  -> Application / Composition Root
       -> Definitions
       -> Memory Policy
       -> Subject / Scope Context
       -> Adapter Injection
  -> Runtime
       -> Agent
            -> Model Protocol
            -> Tool Protocol
            -> Memory Protocol
       -> Workflow
            -> Agent / Tool / Function Steps
            -> WorkflowState
  -> Adapters
       -> Model Provider
       -> Tool Backend
       -> Memory Store
       -> State Store
  -> External Systems

Runtime / Core
  -> Events / Results / Errors
  -> Observability / Test Evidence
```

依赖方向固定为：

```text
Interface -> Application -> Kernel Contracts
Adapter   -> Kernel Contracts
Kernel    -X-> Interface / Application / Provider SDK / Concrete Store
```

## 5. 核心模块边界

| 模块 | 主要职责 | 非职责 |
|---|---|---|
| Runtime | run_id、生命周期、取消、恢复验证、事件和唯一终态 | Agent 推理、Workflow 流程语义、Memory 存储 |
| Agent | Instructions、ModelRequest、Tool Call 循环、Memory Policy 执行 | Workflow 调度、Run 生命周期、具体存储 |
| Workflow | 步骤拓扑、顺序、分支、并行、流程位置、WorkflowState | 模型生成、Memory 存储、恢复令牌校验 |
| Model | Provider Neutral generate / stream | Tool 执行、Prompt 所有权、Memory |
| Tool | 结构化输入输出和一次受治理 Backend 调用 | 自然语言推理、Workflow 路由 |
| Memory | scope 分区、存储、读取、搜索和序列化 | 判断记忆内容、自动共享、WorkflowState、Checkpoint、Trace |

Execution 的 RunContext、Hooks、Guardrails、Retry、Cancellation 和 Streaming 是支撑
协议，不新增第七个核心原语。

## 6. Memory 架构

### 6.1 统一能力与分区

Memory 是统一 Protocol。Application 可以为多个 Agent、Session、用户和项目注入同一个
Adapter。Application 和 Agent Policy 先确定授权范围，数据分区再由每次调用的显式
scope 决定，而不是由 Adapter 实例身份决定。

```text
Shared Memory Adapter
  -> session scope: session-A
  -> session scope: session-B
  -> user scope: user-1
  -> user scope: user-2
  -> project scope: project-X
```

不同分区默认互不可见。

### 6.2 scope 语义

| scope | 内容 | 默认读取者 |
|---|---|---|
| 会话级 | 当前会话局部上下文、临时偏好、中间结论 | 当前 Session |
| 用户级 | 跨会话稳定偏好、经确认事实和长期画像 | 同一用户的授权 Session |
| 项目 / 共享级 | 项目约定、团队共识和授权共享信息 | 被授权项目成员 |

E1 冻结具体 Python 字段和复合键。当前架构只冻结语义、隔离和授权要求。

### 6.3 所有权

```text
Application -> Policy、主体身份、可授权 scope
Agent       -> 读取 scope 集合、写入目标、MemoryItem 内容和来源
Memory      -> 存储、搜索、序列化、scope 隔离
Runtime     -> run_id、生命周期、事件引用
```

Memory Adapter 不判断哪些内容值得记忆，也不根据相似度、session_id 缺失或共享实例
自动扩大读取范围。

### 6.4 Memory Policy

Agent Memory Policy 至少覆盖：

- 允许读取的 scope 集合。
- 默认写入目标。
- 允许提升到用户级或项目级的条件。
- 多 scope 结果排序、去重和上下文预算。
- 主体授权、敏感信息、过期、删除和冲突处理。

Application 创建只读 Policy，Agent 在每次运行中执行 Policy。

### 6.5 MemoryItem

MemoryItem 保存提炼后的可复用信息：

- 内容。
- 来源引用。
- 创建时间。
- 可选元数据。

来源可指向 run、session 或前序 MemoryItem。MemoryItem 默认不保存完整聊天历史，也不
保存 WorkflowState、Checkpoint、Trace、UI 历史、完整 Tool Call 历史或业务数据库
事实。

当前 `ModelMemoryItem` 只是进入 ModelRequest 的只读投影。

### 6.6 跨会话共享与提升

```text
Session A 产生会话级 MemoryItem
  -> Policy 判断内容可跨会话复用
  -> Agent 在 user / project scope 创建新 MemoryItem
  -> 新条目引用原条目或原 run / session
  -> Session B 的 Policy 显式允许读取目标 scope
  -> Adapter 在授权后返回
```

禁止修改原条目的 scope 或静默移动数据。原始条目和提升条目必须能独立过期、删除和
撤销权限。

## 7. 运行数据流

### 7.1 Agent

```text
AgentInput
  -> Runtime 创建 RunContext
  -> Application 提供 scope 上下文
  -> Agent 按 Policy 读取 Memory
  -> Agent 组装 Instructions、Input、MemoryItems、Tool Schemas
  -> Model.generate / stream
  -> Tool Call 循环或最终 AgentResult
  -> Agent 创建 MemoryItem 并选择目标 scope
  -> Memory.write
  -> RuntimeResult + Terminal Event
```

### 7.2 Tool Call

```text
Model ToolCall
  -> Agent 校验 allowed Tools
  -> ToolInput Schema
  -> Guardrail / Permission / Cancellation / Idempotency
  -> Tool Backend
  -> ToolResult
  -> Agent 放入下一次 ModelRequest
```

### 7.3 Memory

```text
Policy + Scope Context
  -> allowed read scopes
  -> Application / Agent Policy authorization
  -> Adapter explicit scope isolation
  -> read / search
  -> Agent ranking / dedup / budget
  -> ModelRequest projection
  -> target write scope
  -> MemoryItem + source
  -> Event reference
```

### 7.4 Workflow 与恢复

```text
WorkflowInput
  -> WorkflowState
  -> Step Scheduler
  -> completed / failed
  -> 或 paused + WorkflowState

resume_input + resume_token
  -> Runtime 校验 token、Run、Checkpoint
  -> Workflow 从明确位置继续
```

WorkflowState 是流程恢复事实源，Memory 不能替代 WorkflowState；Checkpoint 属于
Runtime，Session 历史也不能代替恢复协议。

## 8. 公共契约与数据所有权

| 语义 | 表达 |
|---|---|
| 可替换行为 | `typing.Protocol` |
| 只读装配 | frozen dataclass |
| Input、Result、Event、State | strict frozen Pydantic Schema |
| 运行时失败 | `KernelError` |
| 序列化失败证据 | `ErrorInfo` |
| 稳定状态 | `str Enum` |

必须保持：

```text
AgentDefinition != AgentInput
WorkflowDefinition != WorkflowInput
WorkflowState != Memory
Session != Memory
Checkpoint != Memory
RunContext != WorkflowState
RuntimeResult != AgentResult != WorkflowResult != ToolResult
```

Memory 最终字段由 E1 确认，但不得使用万能 metadata 代替 scope、授权或来源字段。

## 9. Adapter、部署与实现状态

| Contract | 第一阶段实现 | 后续替换 |
|---|---|---|
| Model | Volcengine Ark Adapter | 其他 Provider |
| Tool | 无副作用结构化 Tool | HTTP、MCP、数据库、本地函数 |
| Memory | In-memory Adapter | 文件、数据库、语义检索 Store |
| State Store | 第一阶段最小实现 | 持久化 Checkpoint Store |

当前只落地 Model MVP。Memory E1-E6 全部待开始，本版本不创建 Memory 代码目录，不
引入数据库、向量数据库或生产权限系统。

## 10. 相对基线的差异

- 从单一模糊 scope 扩展为会话级、用户级和项目 / 共享级语义。
- Application 新增提供主体身份、scope 上下文和 Memory Policy 的明确职责。
- Agent 的 Memory 所有权扩展为读取 scope 集合和写入目标选择。
- Memory Adapter 明确不能自动跨 scope 共享。
- 跨会话共享明确使用目标 scope 新建条目和来源链。
- K-006、RD-004 和 E1-E6 的验收口径同步更新。

六个核心原语、单向依赖、WorkflowState 和 Runtime 恢复所有权不变。

## 11. 兼容性与迁移

当前 Memory 尚未实现，没有运行时数据迁移。历史规格和设计记录保持只读。

后续 E1 实现必须：

- 使用稳定 scope 表达分区，不以单一 session_id 代替全部长期记忆。
- 让共享 Adapter 实例通过 Contract Test 证明隔离。
- 让跨 scope 提升创建新条目并保留来源。
- 让持久化 Adapter 替换不改变公共 scope 语义。

未来新增组织级或租户级 scope 时，需要新的规格和架构版本判定。

## 13. 验收标准

- 会话级、用户级和项目级 scope 语义可被稳定表达。
- 同 scope 可召回，未授权跨 scope 不可见。
- 同一用户跨会话共享必须显式读取用户级 scope。
- 项目共享必须满足项目身份和授权。
- 提升创建新 MemoryItem，原条目不变，来源链可追溯。
- 共享 Adapter 实例不破坏隔离。
- MemoryItem 不包含 WorkflowState、Checkpoint 或完整聊天历史。
- 第一阶段仍可仅使用 In-memory Adapter 完成 K-006 和 RD-004。
