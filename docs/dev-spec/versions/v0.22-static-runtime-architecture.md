## 2. 变更原因

原第五章把代码依赖、运行调用、公共字段、配置、测试 Fixture 和物理目录放在同一视图中，难以判断“谁依赖谁”“谁在什么时候调用谁”以及“谁可以修改状态”。

同时，Agent 和 Workflow 的长期定义被混入每次调用 Input，WorkflowState 持有 Runtime 的恢复令牌，Memory 写入决策也没有明确所有者。

## 3. 新增内容

- 静态架构与运行时架构两张独立视图。
- Definition 与 Input 分离规则。
- Agent、Workflow、Memory、Runtime 的状态所有权表。
- 六个 Core 的语义级公共契约。
- ModelRequest、ModelResponse、RunContext 和 WorkflowState 支撑协议。
- Adapter 创建、配置校验和依赖注入规则。
- 物理目录的独立确认门禁。

## 4. 关键决策

### 4.1 Definition 与 Input 分离

```text
AgentDefinition != AgentInput
WorkflowDefinition != WorkflowInput
```

Model、Tools、Instructions 和 Memory 使用配置属于 AgentDefinition；Steps 和流程拓扑属于 WorkflowDefinition。每次调用的 Input 只携带本次任务数据、scope 和调用元数据。

### 4.2 Memory 写入所有权

```text
Application 提供 Memory 使用配置
Agent 决定读取和写入时机
Agent 创建带来源的 MemoryItem
Memory 负责存储、搜索和 scope 隔离
Runtime 提供 run_id 和事件引用
```

Memory 不判断什么值得记忆，也不保存 WorkflowState、Trace 或业务数据库事实。

### 4.3 暂停恢复所有权

```text
Workflow -> 流程位置、已完成步骤、Step Results、WorkflowState
Runtime  -> Run 生命周期、恢复请求校验、一次性 resume_token
```

`resume_token` 不属于 `WorkflowState`。恢复时 Runtime 先验证 token 和 Run 状态，再把对应 WorkflowState 交给 Workflow 继续执行。

### 4.4 物理目录待确认

此前出现的扁平 Core 布局和 `core` 嵌套布局都被取消，不再保留可被误认为实现依据的路径示例。

目录必须在首个模块实现前，根据公共 API、支撑协议归属、Adapter 组织和测试组织单独展示并确认。

## 7. 测试和验收

- 静态依赖图和运行时调用图同时存在，且职责不混淆。
- 六个 Core 都有 Definition/Input、调用、结果、错误和非职责说明。
- AgentDefinition 与 AgentInput、WorkflowDefinition 与 WorkflowInput 明确分离。
- Agent、Memory 和 Runtime 在 Memory 链路中的所有权明确。
- WorkflowState 不包含 resume_token。
- Runtime 拥有恢复请求校验和 resume_token。
- 当前事实源中不存在有效的 Kernel 物理目录树。
- 文档版本、索引、标题层级和关联链接保持一致。

## 8. 架构版本影响

本版本确认首个 Kernel 架构基线形成前的语义边界，并取消尚未确认的物理目录声明。当前仍未发布 `docs/architecture/versions/` 下的首个完整架构正文，因此本次不创建不完整架构快照。

正式进入代码实现前，仍需按照实现准入门禁确认物理目录、Python 类型表达和首个完整架构版本的创建时点。
