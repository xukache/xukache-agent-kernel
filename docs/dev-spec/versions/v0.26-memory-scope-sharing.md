## 2. 变更原因

v0.25 已区分 Session、WorkflowState、Durable Memory 和 Checkpoint，但 Memory 仍只有
单一 `scope` 描述，无法指导会话隔离、同一用户跨会话共享、项目共享和权限验收。

本版本将 Memory 从“按一个 scope 读写”的抽象补充为“统一 Adapter 下按多个 scope
分区，并由 Agent Memory Policy 显式选择读写范围”的完整语义。

## 3. 新增内容

- 确认会话级、用户级和项目 / 共享级三类 scope 语义。
- 明确一个 Memory Adapter 可以服务多个 scope，但不会隐式共享数据。
- 明确 Application 提供主体身份和 Memory Policy。
- 明确 Agent 选择读取 scope、写入目标和 MemoryItem 来源。
- 明确 Memory Adapter 只负责存储、搜索、序列化和 scope 隔离。
- 明确跨会话共享通过用户级或项目级 scope 完成。
- 明确跨 scope 提升需要创建新的带来源 MemoryItem。
- 明确 MemoryItem 默认保存提炼后的可复用信息，不保存完整聊天历史。
- 补充 Memory 与 Session、WorkflowState、Checkpoint、Trace 和业务数据库的边界。

## 4. 修改内容

- K-006 从“同 scope 召回”扩展为“写入、隔离和授权共享”。
- RD-004 增加会话级隔离、显式用户级共享和其他用户不可见证据。
- E1、E3、E4、E5、E6 的交付和验收同步 Memory scope 与提升语义。
- Memory 读写流增加 scope 上下文解析、授权检查、排序、去重、预算和目标 scope。
- 长期语义 Memory 的准入条件增加 scope 授权和跨 scope 提升策略。

## 5. 受影响模块

- Application / Composition Root。
- Agent 和 AgentDefinition。
- Memory Protocol 与 Memory Adapter。
- ModelRequest 的 Memory 投影组装。
- Runtime Events 中的 scope 与来源引用。
- Memory Contract、Integration 和 RD-004 测试。

不改变：

- 六个核心原语的数量。
- Kernel、Application、Interface 和 Adapter 的总体依赖方向。
- WorkflowState、Checkpoint 和 Runtime 恢复所有权。
- 第一阶段使用 In-memory Memory Adapter 的技术决策。
- E1-E6 的任务数量和待开始状态。

## 6. 依赖和兼容性

当前 Memory 尚未实现，因此没有运行时数据迁移。B1 已实现的 `ModelMemoryItem` 继续
作为 ModelRequest 只读投影，不被视为完整 MemoryItem。

E1 实现时必须基于本版本确认 scope 与 Policy 契约；不能因为 In-memory Adapter 简单
而把所有数据放入无分区列表，或把 session_id 当作唯一长期记忆边界。

## 7. 迁移策略

- 不修改历史 v0.25 及更早规格版本。
- 当前完整规格更新为 v0.26。
- E1 冻结字段后，再建立对应代码和 Contract Tests。
- 后续引入持久化 Store 时，通过 Memory Protocol 替换 Adapter，不改变 scope 语义。
- 如果未来增加组织级或租户级 scope，需要新增规格和权限验收，不能复用模糊
  metadata 静默扩展。

## 8. 测试和验收标准

- 同会话 scope 写入后可召回。
- 另一个会话不能读取前一会话的会话级 Memory。
- 同一用户只有在 Policy 允许读取用户级 scope 时才能跨会话召回。
- 其他用户和未授权项目不能读取目标 MemoryItem。
- 跨 scope 提升创建新条目，原条目保持不变，来源链可追溯。
- 同一个 Adapter 实例服务多个 scope 时仍保持隔离。
- MemoryItem 不包含 WorkflowState、Checkpoint 或完整聊天历史。
- `git diff --check` 和 Markdown 链接检查通过。

## 9. 架构影响
