## 2. 变更原因

v0.22 正确冻结了 Definition/Input、Memory 和暂停恢复所有权，但第五章开头只有简化依赖图。该图无法让读者一眼看到：

- 外部请求如何进入 Kernel。
- Runtime 如何治理 Agent 或 Workflow。
- Agent 如何形成 Model、Tool 和 Memory 循环。
- Workflow 如何调度步骤。
- Adapter 如何连接外部实现。
- Events、Results 和 Errors 如何形成运行证据。

用户复审后明确指出：依赖草图不能替代整体架构图。第五章因此退回重构。

## 3. 设计原则

本版本不机械复制参考 RAG 项目的业务组件，而是学习其表达方式：

1. 第一张图必须展示系统全貌。
2. 每个核心层内部继续展开关键组件。
3. 抽象契约、参考实现和外部系统必须连通。
4. 整体图之后再拆分顺序数据流。
5. 所有权规则用于解释架构，不能替代架构图。

## 5. 新增表达

整体架构图现在同时展示：

- External Callers。
- Interface 与 Application / Test Composition Root。
- Runtime 与 Execution Governance。
- Agent Engine 内部的 Memory、Model、Tool Call 循环。
- Workflow Engine 内部的 WorkflowState 和 Step Scheduler。
- Model、Tool、Memory Contracts。
- Adapter Layer 和 External Systems。
- Structured Evidence 与 Observability。

四条数据流分别说明：

- Agent 从输入到结果。
- Tool Call 从模型意图到结果回传。
- Memory 从策略、读取、使用到写入。
- Workflow 从初始状态到暂停和恢复。

## 6. 保留的 v0.22 决策

以下语义没有改变：

```text
AgentDefinition != AgentInput
WorkflowDefinition != WorkflowInput

Agent 创建 MemoryItem 并决定 Memory 使用时机
Memory 负责存储、搜索和 scope 隔离

Workflow 拥有 WorkflowState
Runtime 拥有 Run 生命周期和 resume_token
```

六个 Core 的职责、错误和结果语义继续有效。

## 8. 验收标准

- 第五章第一张图能够看到入口、Kernel、Adapter、外部实现和证据出口。
- Agent Engine 内部明确显示 Memory Read、Model、Tool Call 和 Memory Write。
- Workflow Engine 内部明确显示 WorkflowState、Step Scheduler 和步骤类型。
- Adapter 与对应 Contract 和外部系统形成连续连接。
- Runtime、Agent、Workflow、Model、Tool、Memory 和 Execution 都有独立模块说明。
- Agent、Tool Call、Memory、Workflow 四条数据流完整。
- v0.22 所有权规则未丢失或反转。
- 物理目录继续标记为待确认。

## 9. 架构版本影响

本版本改变架构表达层次，不改变 v0.22 已确认的系统边界、依赖方向或状态所有权。首个完整架构版本尚未发布，因此不创建新的 `docs/architecture/versions/` 正文。
